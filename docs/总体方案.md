# Memory 总体方案

> AI agent 记忆框架：给外部 agent（codegen / docgen / 未来的方案生成）提供跨 session 的经验积累能力。
> 框架本体负责存储、检索、注入、演化；任务向业务逻辑留给各 agent，通过可插拔组件接入。
> 架构决策记录见 [decisions.md](decisions.md)。

## 1. 架构

```
外部 agent ──http / MCP──→ 接入模块（协议翻译 + 校验）
                            ↓
                      编排模块（workspace 路由 + 请求分发）
          ┌──────────┬──────────┼──────────┬──────────┐
       检索模块    注入模块    采集模块    演化模块    存储模块
       search/get  /prompt     events/     L0→L1→     SQLite +
       混合检索    场景注入     ingest/     facts→     文件读写
                   (推)        Phoenix拉    scene→通用
```

| 模块 | 功能 |
|---|---|
| 接入模块 | 翻译外部请求：http / MCP（工具与注入接口），统一校验 |
| 编排模块 | workspace 路由 + 请求分发 |
| 检索模块 | search 混合检索 + get 全文获取（agent 主动拉） |
| 注入模块 | 常驻通用 scene + 任务相关 scene（编排层推，不靠 agent 自觉） |
| 采集模块 | 接收 agent 运行事件 + 文件导入 + OTel 日志流 |
| 演化模块 | L0 → L1 → facts → scene → 通用升级 |
| 存储模块 | SQL + 文件读写，全项目唯一数据出入口 |

## 2. 数据分层

- **L0 原始层**（append-only，文件系统）：doc 原始文件、code 仓库全量拷贝、session 事件流（一 session 一 jsonl）。
  SQLite 只存元数据（路径/hash/派生状态），用于查找、去重、变更检测、pipeline 触发。
- **L1 派生层**（SQLite，FTS + vec）：
  - doc_chunk：文档切片（parent+child），切片 + 摘要 + 嵌入
  - code_graph：tree-sitter 解析的符号/边/文件，FTS 建符号名
  - code_wiki.md：LLM 生成的仓库概览
  - trace：LLM 从 session 事件流提炼的叙事摘要（这次任务干了什么）
- **L2 经验层**：
  - facts：单条事实，workflow / error / finding 三类，带 scenario + topic + confidence
  - scene.md（场景口袋书）：同场景 facts 聚合，四分区（工作流/踩坑/关键发现/演变过程），
    ≤2000 字，≤15 个场景，.md 为真源 + SQLite 做索引

分层图：[data_layer_pyramid](img/data_layer_pyramid.png)

## 3. 数据类型

| 数据 | 存储位置 | 检索方式 | 查什么 |
|---|---|---|---|
| facts | SQLite | FTS + vec | 文本 query → 全文返回 |
| doc_chunk | SQLite | FTS + vec | query → 摘要 → get 全文 |
| code_wiki.md | .md + SQLite | FTS + vec | query → 摘要 → get 全文 |
| code 边 | SQLite | SQL 直查 | 符号名 → 关系查询 |
| code 符号 | SQLite | FTS（符号名） | 符号名 → 位置 + 源码 |
| scene.md | .md + SQLite | FTS + vec | query → 摘要 → get 全文 |

**search 截断规则**（agent 侧行为契约）：content ≤200 字直接返回全文；否则 `content=None` 只返摘要，agent 需要时再调 `get()`。

## 4. 接口

### 4.1 Agent 工具（MCP / http）

1. `search(query, type)` — type: facts / docs / scenes / code，按上述截断规则
2. `get(id_or_name)` — 拿全文
3. `code_explore(query)` — 搜代码，按文件分组返回完整源码
4. `code_graph(symbol, relation, depth)` — relation: callers（谁调了它）/ callees（它调了谁）/ impact（改它影响什么），递归 CTE

### 4.2 注入接口（POST /prompt，编排层调用，LLM 无感知）

1. `load_always_on(workspace)` — 读通用.md 全文
2. `load_catalog(workspace, query)` — 关键词匹配场景 → top-1 scene.md 全文 + 其余场景摘要（heat 排序）

注入产物拼进 agent 的 SystemMessage。"要不要注入"不经过 LLM 决策；
注入的文本自身充当目录（agent 知道能查什么，细目用 search 拉）。
recall 的上限由注入匹配质量决定，不由 LLM 自觉决定。

### 4.3 采集接口

- `POST /events` — session 事件流（TS 插件直推信封），(session_id, seq) 幂等去重
- `POST /ingest_doc` / `POST /ingest_code` — 文件/仓库入库，返回 l0_id（含 hash 命中信息）
- **Phoenix 同步器（docgen 数据源，拉型）** — 定时拉 Phoenix REST/导出 → 翻译成信封 →
  同一 store_events；只导含 done 的完整 trace（失败的运行不进记忆）；docgen 侧零改动零账号。
  映射唯一实现 span_map.py，规则见 [phoenix-sync.md](phoenix-sync.md)。
  （OTLP receiver 曾为此预留，2026-08-24 经真实数据验证 docgen 永不推送而删除）

## 5. 时序

启动时：注入服务把 通用.md 全文 + top-1 场景全文 + 其余场景摘要 拼进 system prompt。
运行时：agent 按需调 search / get / code_explore / code_graph。
后台：事件持续采集 → session 结束触发演化引擎。

时序图：[memory_seq_v3](img/memory_seq_v3.png)

## 6. 演化流程

```
L0 入库（实时/手动）
  → L1 派生（异步：TraceDeriver / DocChunkDeriver / CodeGraphBuilder / CodeWikiDeriver）
  → L2 抽取（LLM 从 trace 抽 facts，每条带 scenario + topic + confidence）
  → facts 去重（embedding 搜相似 → LLM 判 skip / update / merge，同 workspace + scenario + type 范围内）
  → 同场景 facts 累积 ≥3 → LLM 重写 scene.md（读现有 scene + 全部 facts，四分区，≤2000字）
  → 月级跨场景扫描：相似 facts（embedding > 0.85）→ LLM 判断是否通用
     → 合并为通用 fact → 删原 2 条 → 受影响 scene.md 标脏，下次重写时自然更新
```

更新流程图：[data_update_flow](img/data_update_flow.png)

**confidence = sample×0.4 + LLM 自评×0.3 + HITL×0.2 + 使用×0.1**

- sample：验证次数；LLM：抽取自评；HITL：用户反馈（标注修正、评审意见）；
  使用：recall 命中 + 任务结果（如 docgen 的 fill_rate）
- 反馈闭环：注入的 fact 被使用 → 对应任务结果自动回流 → confidence 更新 → 错误经验被淘汰

## 7. Workspace 隔离与存储

- 单 SQLite + workspace 逻辑列（值 = OTel service.name / 接入配置），不用多库
- FTS：workspace 存 UNINDEXED 列，查询 WHERE 过滤
- vec：over-fetch + Python 过滤（万级向量暴力扫，毫秒级）
- `workspace='shared'` 存跨 workspace 共享数据
- SQLite（FTS5 自带 + sqlite-vec 扩展）单文件：零运维、备份即拷文件

## 8. 实例接入

### 8.1 docgen（langgraph，参考文档 → 模板填充）

采集：Phoenix 同步器（拉型，REST 定时拉）；v2 埋点数据含 LLM 完整对话与 thinking。
注入：编排层在 plan 调用前调 /prompt。

与 docgen 组的共识三点：

1. **文件缓存**：reference doc 按 content hash 缓存 + 缓存其任务向 summary
   （键 = doc_hash + prompt_version；memory 只存不算，填 docgen 自己预留的 cache_hit 空位）
2. **plan 注入**（核心）：plan 阶段每次重新推导的字段匹配经验（段位规律、
   一指令多字段共用、CANC 不存在的负面知识）沉淀为 facts/scene 注入，
   推导变核实；fill_rate + 字段级 decisions 自动回流 confidence
3. **标注 HITL**：记录人工修正字段定义的 diff → facts → 辅助下次自动标注；
   修正归零即学会

不承诺：不改其 bounded 架构、不动 summary 业务逻辑、不管单 run 内检索。

**边界**：任务向 summary（docgen 的业务）与检索导向 chunk 摘要（memory 通用）是两回事；
memory 不替 agent 做任务蒸馏，只提供存储、键管理、失效和检索。

**长期**：方案设计类文档生成（无中生有）场景下 memory 价值放大——经验不再是提速手段，
而是内容来源（结构套路、决策一致性、评审反馈闭环、防幻觉接地）。同一套机制，换一个翻译器。

### 8.2 codegen（opencode，有自己的 skill 自改进体系）

关键原则：**嵌入而非替代**。skill = 流程性知识（他们的），facts = 原子经验 + 仓库领域知识（memory 的）。

1. **工具先行**：codegraph + code_wiki，关系型查询（impact/callers）补 opencode 文本工具盲区
2. **facts 供料**：error/finding facts 聚合（"agent 在 Y 模块栽了 4 次同一原因"），
   作为他们 skill 迭代的输入，不夺改进权
3. **仓库惯例知识**：确定性部分走 tree-sitter / wiki；模式类 facts 靠 through-use
   （代码过测试/review 才沉淀），不做无 grounding 的批量抽取

### 8.3 领域知识的沉淀方式

从 trace/plan 沉淀（through-use，带结果背书），不从参考文档批量抽取（无验证、
文档出 v2 即变毒药）。同一领域知识散在多文档时，用月级跨场景升级机制合并。
例外：出现"冷启动痛点"或"跨文档整合需求"时再考虑文档批量抽取单独立项。

## 9. 框架通用性

框架的普适性长在**数据契约**上：统一信封 + put 三动词 + pending 状态机 + workspace 隔离。
场景差异在边界吸收（docgen = span_map，codegen = TS 插件）——新 agent 接入只需写一个
翻译器推信封。Protocol + yaml 注册表是预留的第三层插座（场景组件入驻演化管线），
全部未实现，触发条件与接口草案见 **[components.md](components.md)**
（定位：推迟决策的记录，非冻结契约）。

## 10. 实施

两人团队：框架核心（P0 地基 / P1 走通骨架）共建，之后按场景分叉——
负责人主攻演化引擎 + docgen 场景，队友主攻 codegraph + codegen 场景。
storage 接口与 schema 变更由负责人 review；L2Extractor 由 codegen 复用 docgen 的实现。
任务清单与阶段（P0-P4）见仓库 issue。

代码结构：`src/memory/` 七模块 + `llm/`（唯一 mock 边界）；场景组件目录 Protocol 立项时再建。
